「AIがDBを消した」というニュースの違和感

「AIエージェントが本番のデータベースを消した」という事故報告が、ここ数か月で目立って増えている。

これらの記事を読むと、たいてい主語は「AI」だ。AIが暴走した。AIが間違えた。AIが消した——そういう書き方になっている。

だが少し立ち止まって考えると、構造としておかしい。本番DBに対する DELETE や DROP を実行できる権限を、AIに渡したのは人間だ。テスト環境で十分に検証してから繋ぐ、という普通の手順を抜いたのも人間だ。AIは渡された権限の中でしか動けない。

Dark Readingの分析記事 "AIs So Smart, They Keep Deleting Production Databases" は、この点を冷静に指摘している。事故の本質はAIの知能不足ではなく、組織がセキュリティテストを経ずに本番接続まで一気に進めている運用体制側にある——と。

「誰に渡したらまずいか」のリストにAIが入っていない

責任の所在を整理すると、話は単純になる。

新人エンジニアが入社初日に本番DBへの DELETE 権限を持つことはない。外注の業務委託先に、いきなり本番接続情報を渡すこともない。社内の承認フロー、最小権限、段階的なアクセス昇格——どの組織にも何らかの形で「人間に対する」ガードレールがある。

ところがAIエージェントになると、このガードレールが急に外れる。理由はおそらく単純で、

  • AIは「アカウント」ではなく「ツール」として認識されている
  • 「Claude Codeに繋いでみた」という言い方が、新人を本番に放り込む重みと結びつかない
  • 自然言語インターフェースの軽さが、与えている権限の重さを覆い隠す

このどれもが、組織側の認識のずれだ。AIの問題ではない。本来「人間に渡してはいけない権限」のリストに、AIエージェントが載っていない、というだけの話だ。

「AIには触らせない」では解決しない

ここで「だからAIにはDB操作させるな」と言いたくなる。だがそれは半分正解で、半分ずれている。

仮にAIに触らせなくても、同じ権限を持つ人間（インターンでも、深夜疲労で判断が鈍ったエンジニアでも）が同じ事故を起こす可能性は残る。本番DBに対する破壊的クエリを誰でも一撃で投げられる構造そのものが脆弱で、AIはその脆さを「速く・大量に」露呈させた触媒にすぎない。

だから対策は、AIを名指しで遮断することではなく、

  • 読み取り専用の接続から始める
  • DELETE / DROP / TRUNCATE には必ず人間の承認を1段挟む
  • 練習用 → 確認用 → 本番、の境界を権限レベルで分ける
  • 本番接続情報はそもそも開発端末から触れない経路に置く

という、人間にもAIにも等しく効く設計に戻る話になる。これは古典的な最小権限原則そのものだ。AI時代に新しいことが要求されているのではなく、古い原則を改めて適用する場面が来ただけだ。

商用ガードレールが立ち上がり始めている

5月7日にShow HNに登場した Tilde.run は、まさにこの空白に商用ソリューションを置きにきた事例だ。AIエージェントを「fresh isolated container」で走らせ、全ファイル変更とネットワーク要求を監査記録し、操作ごとに人間の承認ゲートを挟める仕組みを売っている。失敗したら瞬時にロールバックする。

似た方向で、Anthropic自身もエージェント実行のサンドボックス化を強めている。Cloudflareは5月6日に、エージェントに対してStripe経由で月$100の支出上限を強制する仕組みを発表した。「AIに権限を渡すなら、その範囲を金額・時間・対象で物理的に制限する」という設計が、市場の前提になりつつある。

注目すべきは、これらが「AIを賢くする」方向ではなく、「AIが賢くなくても事故らない箱を作る」方向で動いていることだ。事故の本質をAI能力ではなく組織設計の側に置いた、Dark Readingの分析と整合している。

自分の現場ではどうするか

私自身、Claude CodeにDB操作を任せる場面が増えている。便利さの裏で、「とりあえず読み取り専用から始める」という基本がしばしば抜ける。手順を踏んで権限を分けるのは面倒で、その面倒を省くたびに、いつかの自分が消す予定の何かに近づいている。

具体的に取れるアクションは派手ではない：

  • 開発端末からは原則として本番DBに直接繋がない（踏み台と承認フローを通す）
  • AIエージェントに渡すDB接続は、最初は read-only ロールから始める
  • 破壊的クエリ（DELETE / DROP / TRUNCATE / UPDATE 全行）は、AIが組み立てても人間の承認なしには実行されない構成にする
  • 自社プロダクトにAIエージェント機能を載せるなら、お客様側でも同じ権限分けが選べる設計にしておく

最後に繰り返しておきたい。AIが本番DBを消す事故は、AIが愚かだから起きているのではない。本番DBに対する破壊的権限を、検証もガードもなく外側に開いた組織の判断が起こしている。叱るべき相手を間違えると、対策の方向もずれる。
